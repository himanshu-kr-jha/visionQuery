# VisionQuery v1 plan

v1 is done when an investigator can ask "where did the man in the red jacket go after gate 2 yesterday afternoon?", pick the right person from Candidates, follow him across cameras, confirm or reject each proposed Link, and get an Answer whose every statement opens to its Evidence and which states its Gaps.

Each milestone ends in something demonstrable end to end on the dev stack, not a finished layer.
Status markers: `[ ]` not started, `[~]` in progress, `[x]` done.

## M0 Scaffold `[x]`

- `uv` workspace with the packages named in `CLAUDE.md`, plus `web/` (React, TypeScript, Vite).
- ruff, pyright strict, pytest, import-linter contracts, pre-commit, CI running all of them.
- Checksummed append-only SQL migration runner (adapted from phyOS `phyos-provision`).
- Docker Compose: Postgres with TimescaleDB and pgvector, MediaMTX, Triton; profiles `gpu`, `dev`, `observability`.
- `dev` profile: a fake camera publisher that loops sample videos into MediaMTX as several cameras.
- Prometheus metrics endpoint convention for every process.
- Replace the Commands section of `CLAUDE.md` with the real commands.
- README setup from a fresh clone, `make bootstrap`, and a CI job that runs it as written.

**Demo:** from a fresh clone, `make bootstrap` and `make up COMPOSE_PROFILES=dev` bring the stack up healthy with fake cameras, and CI is green on an empty skeleton.

## M1 Cameras and Footage `[~]`

- Camera registry in `memory`; adding a camera by URL (pull) or as a publish path (push).
- Reconciler that makes MediaMTX paths match the registry.
- `recorder`: copy-only fMP4 segments, epoch-aligned, crash-safe, NTP-anchored timebase (adapted from phyOS Photon), plus a segment index in Postgres.
- Camera-offline and recorder-down periods recorded as Gaps from the start.
- Footage playback API (fMP4/HLS over the stored segments) and a minimal web page: camera list, live view over WebRTC, scrub through Footage.
- End-to-end test: publish to MediaMTX, segments appear, playback returns the right instant.
- Layering contract: `tools` and `linker` never import `reasoner` or `api` (M1.8, #67).
- Least-privilege database roles for the services and the Postgres exporter (M1.9, #74).
- Api health follow-ups: a "checking" state, one time budget, URL options (M1.10, #88).

**Demo:** add three fake cameras in the UI, watch them live, scrub back ten minutes, and see a Gap where a camera was stopped.

## M2a Model spike `[ ]`

Done before M2 code is written, on the actual dev GPU.

- Pick and benchmark the person detector, tracker (ByteTrack vs OC-SORT), person ReID model, and CLIP variant: throughput per GPU at 8 fps, and accuracy on footage representative of target sites.
- Pick the local Reasoner and the vision-language model for Descriptions, and measure memory headroom next to perception.
- Build the first evaluation set: footage from at least four cameras with hand-labelled cross-camera identities.
  It is the yardstick for M4 and grows with every Confirmation and Rejection later.
- Record the choices in an ADR if any carry lock-in (for example an embedding size baked into the schema).

## M2 Perception `[ ]`

- Perception Workers that lease cameras, decode with NVDEC at a fixed sampled rate (default 8 fps), and batch detection across cameras through Triton with CUDA shared memory.
- Per-camera tracking producing open and closed Tracks written to `memory` as they happen.
- Keyframe selection per Track; ReID and CLIP embeddings for Keyframes only, batched.
- Lineage on every derived row (camera, segment, model and version) and a processing ledger, so reprocessing with a better model is a query.
- Metrics: lag, frames dropped, inference latency, Tracks per minute per camera.
- Migrations that run outside a transaction, for indexes on populated hypertables (M2.10, #71).

**Demo:** walk through the fake cameras' videos and see Tracks with Keyframes appear in the UI within seconds, including open Tracks.

## M3 Finding people `[ ]`

- Embedding search module in `memory` over day-partitioned pgvector indexes.
- Areas: drawn in the UI, resolved from names.
- Tools: `resolve_area`, `find_candidates` (by description, by photo, by similar Track), `tracks_in`, `gaps`.
- UI: search by description or photo with filters for Area and time; click a person in Footage to pick a Track; confirm an Anchor from Candidates.

**Demo:** type "person in a red jacket near gate 2 between 2pm and 3pm", get ranked Candidates with Keyframes, and set one as the Anchor.

## M4 Linking and Following `[ ]`

- Adjacency: drawn on a camera map in the UI, with walking-time ranges and overlaps.
- Linker: continuous, confident-only Links using appearance plus Adjacency timing; Visits as a rebuildable projection.
- Following: from an Anchor's Visit, forward and backward in time, proposing Links the linker skipped.
- Assertions: confirm, reject, withdraw, all attributed to an Operator; Contradictions surfaced.
- Operators with viewer and investigator roles.
- Learned refinement of Adjacency walking times from confirmed Links, and proposals for missing Adjacencies.
- Measured against the M2a evaluation set: precision of inferred Links, and how much of each true Visit Following recovers.

**Demo:** from one Anchor, see the Visit across cameras on a timeline and map, confirm two proposed Links, reject one, and watch the linker never re-create the rejected one.

## M5 Reasoner and Answers `[ ]`

- `tools` finalised with exact signatures: `resolve_area`, `find_candidates`, `visit_of`, `follow`, `tracks_in`, `describe`, `gaps`.
- Pluggable Reasoner interface with a local default; remote mode sends text and structured facts only, with a test that fails if any Visual Data could cross the boundary.
- Answer builder: statements must cite Evidence returned by tools; uncited statements are removed or flagged; relevant Gaps always included.
- `describe`: on-demand Descriptions of Footage spans by the local vision-language model, stored with their model version and reused.
- Chat panel in the UI rendering Evidence as Keyframes and clips, and handing off to Following when an Anchor is needed.

**Demo:** the v1 definition of done at the top of this document.

## M6 Cases and retention `[ ]`

- Cases: an investigator saves Anchors, Visits, Footage spans and notes; everything in a Case is exempt from expiry until released.
- Footage rolls on a disk budget; Tracks, Keyframes, embeddings and Links expire on their own configurable period; both by dropping day partitions or segments, never by row-by-row deletes.
- Answers state when Footage has expired but Tracks remain.

**Demo:** expire a day of Footage while a Case holds one clip from it; the clip still plays, the rest is gone, and a Question about that day says so.

## Hardening `[ ]`

Follow-ups from reviews that make finished work more robust but that no milestone's demo needs (#86).
Worked whenever the pipeline has a free slot; it never blocks a milestone, and stays open while follow-ups keep arriving.

- `[x]` Migration status, a guard against migrating a foreign database, and a sealed record (H.1, #72).
- `[ ]` Compose stack follow-ups: the stale-project sweep, config errors, the stack tests' port race (H.2, #75).
- `[x]` Fake camera follow-ups: a frozen-write watchdog, the daily rejoin, clock steps (H.3, #82).
- `[ ]` Settings errors: pin the source-error format, name every bad variable, null lists (H.4, #87).
- `[ ]` Attribution check accepts prose; revert titles and commit types agree (H.5, #91).
- `[ ]` Fake cameras document their test-only settings (H.6, #92).
- `[ ]` The foreign-database guard counts every kind of object (H.7, #96).

## After v1
